# DDD 业务分析框架

> 用于 **propose** 阶段。在写 proposal 之前，用此框架分析业务需求，提取 DDD 关键元素，输出结构化的领域分析结果。

---

## 设计顺序（重要）

1. **先设计领域模型**：聚合根、实体、值对象、领域事件
2. **再设计领域行为**：聚合根上的方法（create/modify/delete/changeStatus）
3. **最后设计 UseCase/QueryCase**：
   - UseCase 对应命令（Command）
   - QueryCase 对应查询（Query）

---

## 分析流程

业务需求 → 领域词汇 → 角色定义 → 领域模型 → 领域行为 → UseCase/QueryCase → 不变性约束

---

## 设计原则

1. **所有业务入口来自聚合根**：通过聚合根暴露领域行为，不直接操作内部实体
2. **领域对象不能过小**：避免领域过多导致碎片化，应保持合理的聚合边界

---

## 领域建模原则

### 1. 聚合根(Aggregate Root)设计
- 每个聚合通过根实体访问内部对象
- 聚合内部维护一致性边界
- 聚合之间通过 ID 引用，避免直接对象引用
- **聚合不能太大**：如果聚合过大（并发冲突严重），应拆分成多个聚合根
- **小聚合优先**：聚合越小，并发冲突越少

### 2. 值对象(Value Object)设计
- 不可变对象，通过属性值标识相等性
- 封装业务规则和验证逻辑
- 可复用的领域概念（如 Money、Address）

### 3. 领域服务(Domain Service)设计
- 处理不属于单一聚合的业务逻辑
- 协调多个聚合的交互
- 封装外部系统调用

### 4. 仓储(Repository)设计
- 聚合持久化的抽象接口
- 只能通过聚合根访问聚合
- 提供领域无关的数据访问接口

### 5. 领域行为(Domain Behavior)设计
- 领域行为封装在聚合根上，通过方法暴露业务逻辑
- 不直接暴露 setter，通过领域方法保证不变性
- 常用行为：create()、modify()、delete()、changeStatus()
- 领域行为内聚在聚合根内，保证业务一致性

### 6. 领域事件(Domain Event)设计
- 领域事件表示业务中发生的重要事件
- 命名格式：动词过去式 + 主体（如 OrderCreated）
- 用于解耦聚合间通信，实现最终一致性
- 事件内容应包含聚合 ID 和关键变更信息

---

## UseCase/QueryCase 设计原则

### 1. UseCase（命令）设计
- UseCase 是领域行为的入口，调用领域方法执行业务逻辑
- 每个 UseCase 对应一个命令（Command）
- 命令命名遵循动词+名词规范(如: UpdateParameter、CreateOrder)
- UseCase 只负责协调，不包含业务逻辑

### 2. QueryCase（查询）设计
- QueryCase 提供查询能力，与写入分离
- 每个 QueryCase 对应一个查询（Query）
- 查询命名：`Get[实体]Query`、`List[实体]Query`、`Page[实体]Query`
- 查询直接通过 DAO 获取，不经过领域层

### 3. 命令与查询分离（CQRS）

遵循 CQRS（Command Query Responsibility Segregation）模式：

| 类型 | 数据流 | 返回内容 | 说明 |
|:---|:---|:---|:---|
| **UseCase（命令）** | Controller → UseCase → Domain → Repository | **DTO** | Data Transfer Object，写操作后返回 |
| **QueryCase（查询）** | Controller → QueryCase → DAO | **View** | 查询结果视图，读操作直接返回 |

### 4. DTO/View 结构规范（重要）

**聚合根与实体的包含关系必须体现在 DTO/View 中**：

| 聚合结构 | DTO 结构 | View 结构 |
|:---|:---|:---|
| 聚合根 + 无内联实体 | 扁平 DTO（仅聚合根字段） | 扁平 View |
| 聚合根 + 内联实体 | 嵌套 DTO（聚合根 + items[]） | 嵌套 View（聚合根 + items[]） |
| 聚合根 + 值对象 | DTO 内直接包含值对象字段 | View 内直接包含值对象字段 |

## 分析输出模板

### 步骤 1：提取领域词汇

从需求中识别核心业务概念：

| 术语 | 定义 | 英文 |
| :--- | :--- | :--- |
| [术语1] | [定义] | [英文] |
| [术语2] | [定义] | [英文] |

### 步骤 2：识别角色

区分业务主体、外部系统、内部触发器：

| 角色类型 | 说明 | 示例 |
|----------|------|------|
| **主动角色** | 发起操作的实体 | 用户、管理员 |
| **被动角色** | 被操作的实体 | 客户、订单 |
| **外部系统** | 第三方 API | 支付网关、消息队列 |
| **内部触发器** | 后台 Job | 定时任务、事件监听 |

输出：

| 角色 | 类型 | 职责描述 |
| :--- | :--- | :--- |
| [角色1] | 主动 | [职责] |

### 步骤 3：识别聚合边界

**聚合根特征**：
- 是业务的主人，控制其他对象的生命周期
- 有明确的边界，内部对象不能独立存在
- 保证一致性约束
- 是事务的边界

**验证问题清单**：
1. 内部对象能否独立存在？（不能 → 在聚合内）
2. 是否需要通过外部访问内部对象？（需要 → 独立聚合）
3. 修改内部对象是否需要访问聚合根？（需要 → 在聚合内）
4. 删除聚合根时，内部对象是否一起删除？（是 → 在聚合内）

输出：

**聚合根**: [名称]
**聚合内实体**: [名称列表]

### 步骤 4：识别实体与值对象

| 类型 | 特征 | 示例 |
|------|------|------|
| **实体** | 有唯一标识，有生命周期 | Order、User |
| **值对象** | 无标识，不可变，描述属性 | Money、Address、Age |

### 步骤 5：设计领域行为

| 行为 | 方法名 | 参数 | 触发场景 | 说明 |
|------|--------|------|----------|------|
| 创建聚合根 | create() | attr | 用户提交创建请求 | 创建新聚合根实例 |
| 修改聚合根 | modify() | attr | 用户提交修改请求 | 修改聚合根属性 |
| 删除聚合根 | delete() | - | 用户点击删除按钮 | 删除聚合根 |
| 状态变更 | changeStatus() | newStatus | 管理员审核通过/拒绝 | 状态机流转 |

### 步骤 6：设计 UseCase / QueryCase

**UseCase（命令）**：

| 命令 | 命令内容 | 返回内容 (DTO) | 触发场景 | 说明 |
|------|----------|----------------|----------|------|
| CreateXxxCmd | code, name, description | XxxDTO | 用户提交创建请求 | 创建命令 |
| ModifyXxxCmd | id, name, description | XxxDTO | 用户提交修改请求 | 修改命令 |
| DeleteXxxCmd | id | Void | 用户点击删除按钮 | 删除命令 |

**QueryCase（查询）**：

| 查询 | 查询条件 | 返回内容 (View) | 触发场景 | 说明 |
|------|----------|-----------------|----------|------|
| GetXxxQuery | id | XxxView | 用户查看详情页 | 根据ID查询 |
| ListXxxQuery | code, name, status | List\<XxxView\> | 用户进入列表页 | 列表查询 |
| PageXxxQuery | code, name, status, pageNum, pageSize | PageResult\<XxxView\> | 用户翻页或筛选 | 分页查询 |

### 步骤 7：识别领域事件

**命名格式**：动词过去式 + `<主体>`
**示例**：`OrderCreated`、`PaymentCompleted`

| 事件 | 事件内容 | 触发源 | 触发场景 | 说明 |
|------|----------|--------|----------|------|
| XxxCreated | aggregateId, code, name | 创建操作 | 用户提交创建请求 | 实体创建完成 |
| XxxModified | aggregateId, modifiedFields | 修改操作 | 用户提交修改请求 | 实体修改完成 |
| XxxDeleted | aggregateId | 删除操作 | 用户点击删除按钮 | 实体删除完成 |
| XxxStatusChanged | aggregateId, oldStatus, newStatus | 状态变更 | 管理员审核通过/拒绝 | 状态流转完成 |

### 步骤 8：识别不变性约束

| 约束类型 | 约束内容 | 适用范围 | 示例 |
|----------|----------|----------|------|
| 全局唯一 | 编码全局唯一 | 聚合根 | code 不能重复 |
| 聚合内唯一 | 子实体编码在聚合内唯一 | 实体 | item code 聚合内唯一 |
| 状态规则 | 状态流转必须符合状态机 | 聚合根 | DRAFT→ENABLED→DISABLED |
| 关联约束 | 删除聚合根时必须删除内部对象 | 聚合根 | cascade delete |

## 强制约束

- **禁止生成代码**：本分析只输出 DDD 分析元素，不生成任何代码
- **强制使用表格**：所有输出必须使用 Markdown 表格格式，禁止使用代码块
- **输出文件路径**：由 agent 决定，默认 `docs/[领域名]设计文档.md`
