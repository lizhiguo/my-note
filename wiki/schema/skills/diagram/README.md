# 图表技能 (图驱动开发 / Diagram Driven Development)

这是一个用于维护“统一影响图 (Unified Impact Diagrams)”的综合技能，遵循图驱动开发（DDD）方法论，将用户价值与技术实现紧密连接。

## 概述

此技能帮助你将 `ai/diagrams` 目录维护为系统理解的唯一可信源。与传统技术图表不同，DDD 图表始终展示：
- **前台 (Front-Stage)**：用户看到和体验到的内容
- **后台 (Back-Stage)**：我们如何交付这种体验
- **影响标注 (Impact Annotations)**：为什么每个技术组件对用户至关重要
- **错误路径 (Error Paths)**：发生异常时的处理流程
- **用户价值 (User Value)**：代码到用户收益的清晰连接

## 核心理念

**传统图表回答：“代码做了什么？”**
**DDD 图表回答：“这为什么对用户重要？”**

每一项技术决策都应该能溯源到用户价值，而图表让这种连接变得清晰直观。

## 核心能力

### 1. 创建图表 (Create Diagrams)
为功能、架构、用户旅程、跨部门业务流、数据模型、测试覆盖率和重构计划生成新图表。

**支持的类型：**
- 功能图 (feature-*.md)
- 时序图 (sequence-*.md)
- 架构图 (arch-*.md)
- 流程图 (flow-*.md)
- 跨部门业务泳道图 (lane-*.md，推荐 PlantUML)
- 数据模型 ER 图 (er-*.md，推荐 PlantUML)
- 测试覆盖图 (test-*.md)
- 重构前后对比图 (存放在 refactoring/ 目录下)

### 2. 更新图表 (Update Diagrams)
使图表与代码变更保持严格同步，确保图表始终准确且有用。

### 3. 审计图表 (Audit Diagrams)
- **质量审计**：检查图表是否符合 DDD 原则
- **覆盖率审计**：找出缺少图表的功能
- **同步审计**：找出过时的图表
- **组织结构审计**：确保目录结构和文件命名规范

### 4. 组织图表 (Organize Diagrams)
维护整洁的目录结构和一致的命名规范。

### 5. 索引管理 (Index Management)
持续更新 README.md，使其作为理解系统的入口点。

## 快速入门

### 创建你的第一张图表

1. **理解用户需求**
   - 这个图表解决了什么问题？
   - 它交付了什么价值？

2. **选择图表类型**
   - 功能流程 → `features/feature-{name}.md`
   - 用户旅程 → `journeys/sequence-{name}.md`
   - 系统架构 → `architecture/arch-{name}.md`

3. **阅读 DDD_PRINCIPLES.md**（必读）
   ```
   references/DDD_PRINCIPLES.md
   ```

4. **阅读 CREATE.md 获取模板模式**
   ```
   references/CREATE.md
   ```

5. **使用模板创建**
   - 同时包含前台 (Front-Stage) 与后台 (Back-Stage)
   - 对所有后台技术组件添加影响标注
   - 包含带有恢复机制的错误路径
   - 以用户作为入口和退出点

6. **更新 README.md 索引**

## 使用示例

### 示例 1：新功能图表

**用户请求**："为新的支付处理功能创建图表"

**Agent 工作流**：
1. 读取 `references/DDD_PRINCIPLES.md` 和 `references/CREATE.md`
2. 分析支付功能代码
3. 创建 `features/feature-checkout-payment-flow.md`：
   - 展示用户点击“立即付款”（前台）
   - 展示支付网关、数据校验、订单创建（后台）
   - 添加影响标注（🛡️ 安全保障，💾 保证持久化，⚡ 快速响应）
   - 展示错误路径（支付失败 → 重试选项）
4. 更新 `ai/diagrams/README.md` 索引

### 示例 2：代码修改后更新

**用户请求**："我们在搜索功能中加入了缓存，更新对应图表"

**Agent 工作流**：
1. 读取 `references/UPDATE.md`
2. 找到 `features/feature-search-functionality.md`
3. 在图表中添加缓存层并附带影响标注（⚡ 提速 80%）
4. 更新“最后更新 (Last Updated)”日期
5. 追加变更历史记录条目

### 示例 3：审计图表

**用户请求**："审计我们图表的质量和覆盖率"

**Agent 工作流**：
1. 读取 `references/AUDIT.md` 和 `references/DDD_PRINCIPLES.md`
2. 扫描 `ai/diagrams/` 下的所有图表
3. 按照 DDD 质量检查清单逐一审查
4. 找出没有图表的功能
5. 对比图表修改日期与 Git 提交历史
6. 生成包含改进建议的完整审计报告

### 示例 4：重构前后对比

**用户请求**："我们要加入缓存层以提升性能，请记录这次变更。"

**Agent 工作流**：
1. 读取 `references/CREATE.md`（重构章节）
2. 创建 `refactoring/feature-add-caching-layer.md`
3. 绘制“重构前 (Before)”图表（当前较慢的流程）
4. 绘制“重构后 (After)”图表（包含缓存，使用 `#90EE90` 高亮）
5. 标注性能改善数据（2s → 50ms）
6. 解释用户收益（搜索结果秒级呈现）

## DDD 核心原则（简述）

每个图表必须包含：

✅ **双层视角**
- 前台 (Front-Stage)（用户体验）
- 后台 (Back-Stage)（技术实现）

✅ **影响标注**
- ⚡ 速度 / 性能
- 💾 存储 / 持久化
- 🛡️ 安全 / 防护
- ✅ 校验 / 成功
- ⏱️ 响应度 / 体验
- 🔄 恢复 / 重试
- 📊 数据准确性
- 🎯 功能使能

✅ **以用户为中心**
- 以用户作为入口和退出点
- 用户操作清晰可见
- 用户最终结果明确

✅ **异常处理**
- 展示错误路径
- 包含恢复选项
- 记录降级容灾行为

❌ **严格禁止**
- 脱离用户上下文的纯技术图表
- 缺失影响标注
- 仅有正常路径（无错误处理）
- 自定义颜色（变更部分使用 #90EE90 除外）

完整原则请参阅 `references/DDD_PRINCIPLES.md`。

## 研发流程集成

### 研发工作流

```
1. 规划阶段 (Planning Phase)
   ├─ 查阅现有图表
   └─ 为新功能绘制方案提案图表

2. 实现阶段 (Implementation Phase)
   ├─ 编码时参考图表
   └─ 确保代码符合图表设计意图

3. 完成阶段 (Completion Phase)
   ├─ 更新图表以反映最终实现
   └─ 追加变更历史记录条目

4. 审查阶段 (Review Phase)
   ├─ 借助图表向他人解释变更
   └─ 验证图表与代码的一致性
```

### 协作工作流

```
1. 新人入职 (Onboarding)
   └─ 新开发者阅读图表以快速理解系统

2. 架构评审 (Architecture Reviews)
   └─ 使用图表讨论系统架构设计

3. 代码审查 (Code Reviews)
   └─ 引用图表解释改动影响

4. 文档化 (Documentation)
   └─ 图表作为持续演进的活文档
```

## 质量标准

### 最低要求

每个图表必须具备：
- [ ] 规范的文件结构（Type, Last Updated, Related Files, Purpose, Diagram, Key Insights, Change History）
- [ ] 展示用户体验的前台
- [ ] 展示技术实现的后台
- [ ] 对后台组件添加影响标注
- [ ] 至少一条包含恢复机制的错误路径
- [ ] 合法的 Mermaid 语法
- [ ] 在 README.md 索引中完成登记

### 优质图表特征

- 从起点到终点拥有清晰的用户旅程
- 每个技术组件都有有意义的影响标注
- 展示多条错误路径和恢复选项
- 尽可能量化性能指标
- 记录了关联的代码文件
- 变更历史清晰记录了图表演变
- 核心洞察清晰阐述了用户价值

```
4. 输出按优先级排列的整改清单
5. 安排高优先级图表的更新计划
```

## 最佳实践

1. **保持同步** - 代码改动后立即更新图表
2. **用户优先** - 始终从用户需求出发
3. **展示异常** - 不要只画成功路径
4. **量化影响** - 在标注中使用具体指标（例如 2s → 50ms）
5. **维护索引** - README.md 是系统的入口文件
6. **验证质量** - 保存前对照 DDD 检查清单逐项核对
7. **记录变更** - 变更历史有助于后续追溯理解
8. **阅读参考** - 操作前始终先阅读对应参考文档
9. **测试语法有效性** - 提交前验证 Mermaid 或 PlantUML 语法合法
10. **定期审计** - 月度审计确保图表健康度
11. **动态流转优先泳道** - 跨组件、跨部门或跨服务的动态执行链路，优先使用 PlantUML 泳道图，严禁在 Mermaid subgraph 间反复交叉连线

## 疑难排解

### “我不知道这提供了什么用户价值”

**解决方案**：自问以下问题：
- 这项功能解决了什么问题？
- 如果没有它会发生什么？
- 它如何改善了用户体验？
- 哪项指标得到了提升（速度、稳定性、安全性）？

如果你无法回答这些问题，需要重新评估该功能是否有存在的必要。

### “图表过于复杂”

**解决方案**：
- 拆分为多个图表（总览图 + 详情图）
- 使用子图 (subgraphs) 梳理复杂度
- 为详细流程创建独立的时序图
- 每张图表聚焦于单一维度

### “代码修改了，但我不知道涉及哪些图表”

**解决方案**：
```bash
# 查找引用了修改文件的图表
grep -r "path/to/changed/file" ai/diagrams/

# 检查图表更新日期与 git 提交记录
git log --since="diagram-date" path/to/file
```

### “Mermaid 无法正常渲染”

**解决方案**：
- 将代码复制到 [Mermaid 在线编辑器](https://mermaid.live) 进行排查
- 检查常见语法错误（参见 MERMAID_GUIDE.md）
- 检查括号与方括号是否配对
- 检查连线箭头语法
- 确保声明了图表方向（如 `graph TD`）
